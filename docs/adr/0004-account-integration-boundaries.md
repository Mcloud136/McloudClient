# ADR 0004：账号体系集成的架构边界

- **状态**：提案（2026-11-12，待用户确认）
- **相关**：ADR 0001 / 0002 / 0003、`docs/c2-account-integration-design.md`、`docs/c1-ipc-contract.md` §1、`docs/c1-roadmap-2026-11-12.md`
- **触发**：用户临时变更需求 —— 客户端集成 v2board 账号登录、订阅信息、订阅购买与账户管理。

## 1. 背景

客户端原设计是「手工导入订阅 URL + 只读状态面板」，凭据只以订阅链接形式存在。
新需求要求用户输入邮箱与密码登录，并在客户端内查看账户、购买套餐。
核实的 v2board 1.6.0 用户端 API 显示：`POST /passport/auth/login` 返回的
`auth_data` 是 **`base64(email:password)`**，即长期有效的等价密码，而非可撤销会话 token；
部分分支改用 JWT 并提供会话管理，但客户端应按最坏情况设计。
同时，面板存在自定义补丁且 `update.sh` 的 `git reset --hard` 会覆盖补丁。

## 2. 决策

| 编号 | 决策 |
|---|---|
| **L1** | 密码 / `auth_data` / 订阅 URL 只在 `client-sidecar` 的 `panel` 与 `credential` 模块内以 `Secret<T>` 持有；GUI 只接收脱敏 DTO。`Secret<T>` 不实现 `Debug`/`Display`/`Serialize`，`Drop` 清零 |
| **L2** | 内核服务（`client-core`，session 0）不接收、不存储、不转发任何账号数据；账号态与数据面完全解耦 |
| **L3** | 不引入 WebView：支付二维码用纯 Rust 位图在 egui 渲染，网页支付跳转系统浏览器 |
| **L4** | 只依赖 v2board **标准用户端 API**；DTO 字段全 `Option`/默认值，未知字段忽略；不依赖面板补丁或自定义字段 |
| **L5** | 扩展自有最小 HTTP 客户端（复用已有 `rustls` / `tokio-rustls`），支持 POST / JSON / `Authorization` / 状态码；不引入 `reqwest` |
| **L6** | 保持命名管道**单连接**模型：账号态在 GUI 与 sidecar 同进程内走 `mpsc`，不为账号功能新增内核 IPC 方法 |
| **L7** | 「记住我」默认关闭；开启时只把 `auth_data` 存入按用户隔离的 OS 凭据库，绝不持久化密码；登出 / 改密 / 凭据失效立即清除 |
| **L8** | 订阅 URL 由 `GET /user/getSubscribe` 返回并作为**内存 source** 注入既有快照流程，不再经命令行参数；手工导入保留为兼容与离线入口 |

## 3. 理由

1. **凭据等级决定边界**：`auth_data ≈ 密码`，任何写入 UI 状态、日志、IPC 帧或截图产物都会把一次泄露升级为账号永久失陷。
2. **最小权限**：内核是需要管理员权限、常驻 session 0 的数据面进程；让它持有用户凭据会显著扩大风险面与提权收益。
3. **不推翻 D1**：`egui + glow` 刚由用户裁决定案；支付场景是 WebView 最容易被重新引入的地方，需预先锁死。
4. **供应链与升级韧性**：面板补丁会被 `git reset --hard` 抹掉，标准 API + 宽松反序列化是唯一稳定的耦合面。
5. **保持现有资产**：单连接 IPC、快照 5 版回滚、`reload` 事件、8 套实机回归与 86 tests 全部可复用，账号功能不触碰数据面。

## 4. 后果

**正面**：账号态故障不影响代理；内核契约不变；登录失败可离线使用已缓存订阅；
订阅 URL 不再出现在进程命令行；新依赖数量可控。

**负面 / 成本**：

- L1 是**模块与类型边界**，不是 OS 级进程隔离（GUI 与 sidecar 同进程），需靠 code review 与目录边界维持，不能宣称强隔离。
- 需扩展自有 HTTP 客户端并处理 JSON 错误映射、限流、证书校验，工作量高于直接引入 HTTP 库。
- 新增 `qrcode`、凭据库 crate、`zeroize` 等依赖，必须先过 `cargo deny`（G1 §8.3 第 3 条）。
- 登录页使 PrintWindow/OCR 类实机回归面临凭据入截图的风险，回归脚本须改用假账号并增加防护断言。
- 崩溃转储中的凭据残留是**已知限制**，不声称完全消除。

## 5. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 在 GUI 状态里保存 `auth_data`，按需传给请求函数 | 直接违反 L1；截图、日志、崩溃转储、OCR 回归都会成为泄露面 |
| 内嵌 WebView 加载面板支付页 / 登录页 | 推翻 D1；`auth_data` 与订阅 token 会进入 WebView 层，违反 G1 §8.3 与契约 §6 |
| 让内核服务直接拉取面板 API | 提权进程持有用户凭据，风险面最大；且破坏数据面/控制面解耦 |
| 客户端自行拼接订阅 URL | 生产订阅路径为自定义值，且会固化面板实现细节；L4 要求由 API 返回 |
| 引入 `reqwest` | 依赖树与二进制/内存增长，与低内存约束和 `cargo deny` 成本冲突；已有 TLS 栈可复用 |

## 6. 重新评估条件

满足任一才重新讨论本 ADR：

1. 面板升级为可撤销会话（JWT + 会话撤销），且需要多设备登录态同步；
2. 支付渠道强制要求内嵌网页（此时须重开 D1 评审，而不是局部放宽 L3）；
3. 内核需要按账号维度做流量计费或策略隔离（属架构级变更，需单独评审）。

## 7. 验收信号

- 自动化断言：凭据不落盘、不进日志、不进 IPC 帧、不进截图产物；
- mock 面板服务器覆盖登录、订阅同步、下单、支付轮询、401、429、字段缺失；
- 现有 s5–s12 回归与 86 tests 全绿，内核契约 7 个方法不变；
- `cargo deny` 通过后再引入新依赖。
