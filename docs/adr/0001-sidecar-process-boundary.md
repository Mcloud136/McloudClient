# ADR 0001：sidecar 与内核的进程边界

- **状态**：已接受（架构层，2026-11-12）——内核自研、双进程 + Windows 服务；IPC 与配置/日志归属待定，见 §9
- **日期**：2026-11-12
- **相关**：`docs/benchmark-results/2026-11-12-c0d-windows-poc.md`、`docs/g1-gate-review.md` §6

## 1. 背景

C0d 第 5 条通过线是「`kill sidecar` 后内核存活并自动重连」。这条要求隐含一个前提：**sidecar 与内核是两个进程**，且数据面不依赖控制面存活。

当前 `client-core` 是单进程，同时承担：

- 数据面：SOCKS5 入站、规则路由、VLESS/WS/TLS/mlkem 出站、UDP 中继、fake-ip DNS
- 控制面：CLI 配置、profile 加载、订阅热重载、日志

C0d 实测结果对本决策有直接影响：自研数据面 4/6（TCP+UDP、1 MiB、域名、DNS 无泄漏），Mihomo v1.19.34 仅 2/6——其 UDP/DNS 在普通 SOCKS5 配置下走 DIRECT，规则无法覆盖。

## 2. 决策驱动因素

按权重排序：

1. **UDP/DNS 可控性**：C0d 已证明这是内核选型的决定性差异，不能靠规则补救。
2. **崩溃隔离**：控制面（UI、订阅、状态）崩溃不应中断已建立的代理链路。
3. **权限模型**：TUN 需要管理员权限；GUI 与日常控制不应常驻高权限。
4. **更新粒度**：内核与界面可独立升级，降低发版耦合。
5. **可观测性**：日志、连接状态、健康检查需集中采集。
6. **实现成本**：当前只有单进程实现，拆分有一次性成本。

## 3. 选项

### A. 单进程（延续现状）

`client-core` 继续同时做数据面与控制面，未来把 TUN 也放进来。

- 优点：零拆分成本；无 IPC；调试路径最短。
- 缺点：任何崩溃都断网；TUN 需要整个进程提权；C0d 第 5 条无法满足（无 sidecar 可 kill）。

### B. sidecar + 外部内核（Mihomo）

sidecar 负责订阅、配置下发、状态与日志；Mihomo 作为数据面进程。

- 优点：内核成熟、协议覆盖广；sidecar 崩溃不影响已下发配置的运行；符合 C0d 第 5 条的字面形态。
- 缺点：**C0d 已证明其 UDP/DNS 不可控**；内核行为、版本与体积受上游约束；加密特性支持取决于上游版本；排障需跨两个项目。

### C. sidecar + 自研内核进程（推荐）

把现有 `client-core` 拆为「内核进程（数据面）」+「sidecar（控制面）」，两者通过本地 IPC 通信。

- 优点：UDP/DNS/规则行为完全自有（C0d 已验证）；崩溃隔离成立；TUN 只在内核进程提权；内核可独立升级；后续 GUI 只是 sidecar 的另一个客户端。
- 缺点：需要设计 IPC 与状态机；拆分有一次性重构成本；需要 supervisor 逻辑。

## 4. 对比

| 维度 | A 单进程 | B Mihomo 内核 | C 自研内核进程 |
|---|---|---|---|
| UDP/DNS 可控 | 高 | **低（C0d 实测）** | 高 |
| 崩溃隔离 | 无 | 有 | 有 |
| TUN 权限收敛 | 整进程提权 | 内核提权 | 内核提权 |
| 更新粒度 | 整体 | 内核可换 | 内核可独立升级 |
| 实现成本 | 最低 | 中（集成 + 绕开 UDP 限制） | 中高（IPC + supervisor） |
| 协议演进自主性 | 高 | 低 | 高 |

## 5. 建议

**选 C**。核心理由不是"自研更好"，而是 C0d 给出了一个可复现的负面证据：在需要 UDP 与无泄漏 DNS 的场景下，Mihomo 的默认路径不可控；而这条恰好是代理客户端的核心能力。

C 的形态：

```
sidecar（普通权限）
  ├─ 订阅拉取 / 校验 / 快照
  ├─ 状态与指标（连接数、流量、健康）
  ├─ 环形日志
  └─ supervisor：内核退出后重启并恢复快照
        │ 本地 IPC（JSON lines over named pipe / Unix socket）
        ▼
内核进程（数据面，按需提权）
  ├─ SOCKS5 / TUN 入站
  ├─ 规则、DNS、UDP
  └─ VLESS/WS/TLS/mlkem 出站
```

这样 C0d 第 5 条可验证为：kill sidecar → 内核继续转发既有连接 → sidecar 重启后重新接管状态。

## 6. 后果

正面：

- 第 5 条通过线具备可验证的架构基础。
- TUN 与 GUI 的权限边界清晰。
- 内核可独立发版，不被界面节奏拖累。

负面：

- 需要新增 IPC 协议与版本兼容策略。
- 单机调试从"一个进程"变为"两个进程 + 日志关联"。
- 拆分期间需要保持现有 4/6 通过线不回退（用现有脚本回归）。

## 7. 分阶段落地（建议顺序）

1. **纯重构**：`client-core` 拆为 `client-core-lib` + `client-core-bin`，行为不变，40 tests 不变。
2. **sidecar 骨架**：IPC 通道、`status` 查询、日志转发；内核仍可由 CLI 独立启动。
3. **supervisor**：内核异常退出自动重启、退避、崩溃计数；对应第 5 条。
4. **TUN 归位**：TUN 只在内核进程启用，sidecar 保持普通权限。
5. **GUI**：作为 sidecar 的客户端，不直接接触数据面。

## 8. 待决问题

| 问题 | 选项 | 影响 |
|---|---|---|
| IPC 协议 | JSON lines / Protobuf / gRPC | 版本兼容与调试成本 |
| Windows 运行形态 | 用户会话进程 / Windows 服务 | 开机自启与权限 |
| 配置所有权 | sidecar 持订阅快照 / 内核自行拉取 | 第 5 条的可验证性 |
| 日志归属 | 内核写环形缓冲 / sidecar 聚合 | 崩溃后取证能力 |

以上四项需在进入第 2 阶段前确定；本 ADR 只锁定"进程分离 + 自研内核"这一层。

## 9. 决策记录（2026-11-12）

| 项 | 决定 | 依据 |
|---|---|---|
| 内核归属 | **自研 `client-core`** | C0d 4/6；UDP/DNS 行为可控 |
| 进程形态 | **双进程 + Windows 服务（B3）** | 面向最终用户分发，需安装器与开机自启 |
| IPC | **共享内存环**（待技术评审） | 详见 §9.1 |
| 配置所有权 | **sidecar 推快照（A）** | 内核不持订阅凭据；断网重启仍可用；支持版本回滚 |
| 日志归属 | **待定** | 见 §9.3 |

### 9.1 共享内存环在 B3 下的技术风险

服务运行在 session 0，用户会话在 session 1+，跨会话共享内存需要：

1. 全局命名对象（`Global\` 前缀）与 `SeCreateGlobalPrivilege`；
2. 显式安全描述符（DACL）允许交互用户读写，否则用户侧进程打不开映射；
3. 自行实现同步原语与内存布局版本号；
4. 崩溃后的残留环清理与一致性校验；
5. 无法像命名管道那样用 `PipeSecurity` 直接表达访问控制。

收益方面：控制面消息频率为「每次操作一条」，命名管道往返约 20–80 μs，共享内存约 1–8 μs，差异对用户不可感知。

结论：共享内存环适合**高频指标流**（连接级统计），不适合控制命令通道。建议控制面先用命名管道，把 IPC 抽象为 trait，指标通道保留共享内存的演进空间。

### 9.2 配置所有权：sidecar 推快照（已接受，2026-11-12）

内核不联网、不持订阅凭据，只读本地快照；sidecar 负责拉取、校验、版本化与回滚。选择理由与三案对比见 §4/§5 与 `0002`。

落地时必须实现以下三点，否则"推快照"不成立：

1. **原子写**：先写 `<seq>.json.tmp`，`fsync` 后 `rename` 为 `<seq>.json`；`current.txt` 单独原子替换，避免读到半写文件。
2. **引导快照**：安装包内置最小快照（仅 `DIRECT` 规则），保证首次启动且无网络时内核可启动并显示"未配置订阅"，而不是直接退出。
3. **失败分类**：sidecar 状态须区分 `fetch_failed` / `validate_failed` / `kernel_rejected`，并指数退避重试；拉取失败时继续以当前快照服务，不阻塞数据面。

### 9.3 日志归属：内核写环形文件（已接受，2026-11-12）

日志以文件为权威来源，sidecar 只读展示与导出；仅"崩溃前状态快照"等关键事件走 IPC。详见 `0002` §3。
