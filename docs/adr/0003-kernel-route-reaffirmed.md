# ADR 0003：复核 meow-rs 后维持自研内核 R2

- **状态**：已接受（2026-11-12 用户确认）
- **日期**：2026-11-12
- **相关**：ADR 0001、`docs/g1-gate-review.md` §8、`docs/benchmark-results/2026-11-12-meow-rs-comparison.md`（v2.1）、`docs/client-design-plan.md` §5 / 附录 C

## 1. 背景

2026-11-12 完成与 `meow-rs/meow-rs` v0.29.0 的实机对比。该项目是 Rust 实现的 mihomo 兼容内核：MIT 许可、11 个 crate、多协议、TUN/Wintun、REST API + Web Dashboard，功能面比本项目 C0 / PoC 级数据面大一个数量级。对比后提出是否改为「在 meow-rs 基础上完善」。

## 2. 复核证据

| 项 | 结论 |
|---|---|
| v2 基准（两侧 Release + 双内核并发交错 + 两轮反转顺序） | 冷启动、空闲 RSS/CPU、小请求 p50/p99、1 MiB 吞吐**同档**；5 MiB 吞吐名义差 21%，但样本范围 182–904 MiB/s 完全重叠、两轮自身波动 65%，**不构成性能差异证据** |
| 官方产物加密能力 | 用纯虚构配置（无任何真实凭据）跑 `meow -t`：进入 ML-KEM 密钥解析路径，**已启用 `vless-encryption`**，编译期障碍排除 |
| 许可 | meow-rs 为 MIT，与本项目 MIT 兼容，复用门槛低于原评估中的 GPL Mihomo |
| 配置校验行为 | 加密节点解析失败时仅 WARN + 跳过该 proxy，`-t` 仍返回 `Configuration test passed` / RC=0（行为观察，非投诉根因结论） |

## 3. 决策

**维持 ADR 0001 的自研内核 R2 路线**，不改为基于 meow-rs 完善。C1 继续按低内存原生 GUI（egui + glow）与自有订阅 / 快照 / 服务化架构推进。

## 4. 理由

1. **立项动因在客户端侧**：G1 决议的输入是「Clash Verge 测试显示节点不可用但节点实际可用、换 NekoBox 正常；网络测试与多节点负载均衡异常」。meow-rs 是**内核**、Clash Verge 是**前端**，替换内核不直接解决前端测速与负载均衡问题；若改用其 Web Dashboard，则与低内存原生 GUI 约束冲突。
2. **决定性依据未复测**：ADR 0001 选 R2 的核心是 C0d 中 Mihomo v1.19.34 的 UDP/DNS 负面证据（53 端口硬编码 DIRECT）。meow-rs 作为 mihomo 兼容内核是否继承该行为，未验证。
3. **可控可观测**：G1 已判定现场问题归因不可执行，替代策略是自有、可配置、可导出日志的测速与负载均衡。成为下游会把加密实现、DNS 行为与探测语义的控制权交给上游。
4. **基准不足以改路线**：DIRECT 回环只覆盖「SOCKS5 握手 → `MATCH,DIRECT` → `TcpStream::connect` → `tokio::io::copy` 双向转发」这一段双方共有的最小路径；协议栈、加密记录层、TUN、多节点探测均未参与执行。功能面差距真实，但不是「性能优劣」的证据。
5. **程序性**：G1 已拍板「保持自研 R2」，改路线属于撤销决策，须走正式修订而非代码层替换。

## 5. 重新评估的条件

若下列三项完成后仍倾向复用，再走 ADR 0001 修订 + G1 追认 + `client-design-plan.md` 更新：

1. **真实节点加密链路对比**（需用户授权测试订阅，合法密钥通过 `meow -t`）：握手耗时、加密记录层、1/5 MiB 下载、DNS 无泄漏。
2. **用 C0d 用例复测 meow-rs 的 UDP/DNS 行为**，确认是否继承 Mihomo 的负面证据。
3. **多节点测速与负载均衡语义验证**，直接对应立项动因。

## 6. 性能工作的定位（避免误读基准）

「功能多却性能同档」**不推出**「本项目代码有较大优化空间」：该基准没有让 meow-rs 的额外功能进入热路径，双方执行的是同一段最小转发逻辑；功能多而不带来开销，说明的是其模块化 / 按需加载做得好。同理，本项目在 DIRECT 回环上的数值也不代表真实链路表现 —— VLESS / WS / TLS / `mlkem768x25519plus` 握手与加密记录层在这轮基准里**一次都没运行**。

因此 C1 的性能工作按以下顺序推进，**不在 DIRECT 回环上先做优化**：

1. **真实链路基线**：握手耗时、加密记录层 CPU、WS 帧开销、1/5 MiB 下载、WAN 延迟与多节点探测。
2. **自身三层基线**（附录 C.5）：criterion 微基准 / 组件基准 / 整机回环；Release 构建 + 固定 CPU 亲和与电源计划 + W1–W10 交错多轮。
3. **解释 5 MiB 吞吐 5 倍波动**：页缓存、`curl` 计时口径、tokio 工作线程数、缓冲大小对照（`relay.rs` 用 `tokio::io::copy` 默认缓冲，而 `outbound.rs:93` 的 WS 链路显式用 65536）。
4. **热点门控**（附录 C.3）：只有占比 >10% 才允许 intrinsics / 极窄 `asm!`，必须有标量回退 + proptest + criterion。
5. **FA 计量**：内核 ≤0.2% / sidecar ≤0.3% / UI ≤1.0%（可见）、≤0.2%（托盘），三项分别计量，20 min 窗口。

**结论**：横向微基准的作用是排除「构建形态不对等」这类测量错误，不是给出优化清单。真正的优化输入必须来自自身 profiling 与真实链路基线。
