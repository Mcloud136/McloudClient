## 1. 起点事实（可直接引用）

节点侧已完成 Rust 重构并发布 `v0.2.0`（未部署，四台生产仍跑 `0.1.1`）。支撑后续判断的事实：

| 事实 | 数值 / 说明 |
|---|---|
| 空载常驻内存（同一台 <NODE_HOST>，1 vCPU） | Go 55–64 MB → Rust 7.7–8.0 MB（约 1/7–1/8） |
| 40 条连接后内存 | Go 60–65 MB → Rust 15–22 MB |
| 16 并发 × 1 MiB 服务端 CPU | Go 0.19–0.20 s → Rust 0.11–0.14 s |
| 二进制 | Go 77 MB + 27 MB geo → Rust 约 10.3 MB static-pie musl |
| 协议兼容 | VLESS + WS + TLS，与官方 Xray v26.11.9 双向互通 |
| 独占能力 | VLESS Encryption（`mlkem768x25519plus`）已实现，但生产 `encryption` 全空、未灰度 |
| 质量基线 | 65 单测 + 9 探针 + 8 套 E2E，CI 硬门禁 |

必须说准的一句：**确定性收益是内存、并发、部署形态，不是单用户测速翻倍**。公网经 CF 的测速方差极大（Rust 0.29–3.75 MB/s），不足以支撑「更快」的结论。

## 2. 第一个判断：现在该不该做客户端

### 2.1 原始策略文档的结论

`v2node\node-rust-client-strategy.md` 的结论是：**先别急着开客户端**。它的推理是：

1. 只做节点 → 拿到内存/成本/稳定性，所有用户立即受益，且不需要用户升级客户端。
2. 只做客户端 → 只能跑现成协议，和 Mihomo/Sing-box 没有差异，用户没有迁移理由。
3. 节点 → 客户端 → 收益上限最高，但成本与风险也最高。

它还给了启动客户端的硬指标：节点峰值 CPU 长期 <30–40% 且 RSS 稳定、加密覆盖率被客户端版本卡住、用户投诉集中在客户端侧、或出现必须两端配合的新能力。

### 2.2 我为什么接受这个结论

**因为独占能力还停在地上。** 加密已经实现，但生产一个加密节点都没开。此时做客户端，用户拿到的仍然是 VLESS+WS+TLS——和现有客户端完全一样，纯属换皮。

另一个现实约束：客户端覆盖率数据（目标用户里 Mihomo / Sing-box / Shadowrocket 的版本分布）根本没有。没有这个数据，无法决定先做哪个平台，也无法判断自有客户端能覆盖多少用户。

### 2.3 但任务要求「开始规划」，所以我改了问题的形式

不去争论「做不做」，而是把问题改成：**满足什么条件就做、在此之前能做什么不浪费的投入**。

于是规划被我拆成两段：

- **C0 准备**：现在可做，且即使最终不做客户端也不亏（抽协议 crate、加密灰度、链路 PoC）。
- **C1 起**：需要门控数据通过才启动。

这个处理方式本身是本次规划最重要的判断：**把「要不要做」变成「门控」，避免在证据不足时投入 UI 与内核集成。**

## 3. 第二个判断：如果做，怎么复用协议层

### 3.1 约束

协议实现目前在 `v2node-rust` 这个 **bin crate** 里（`src/vless.rs`、`src/encryption.rs`、`src/tls.rs`）。客户端要复用它，必须先能当库用。

而成熟内核 Mihomo、sing-box 都是 **Go** 写的。这就产生了跨语言复用的三选一。

### 3.2 三条路与淘汰理由

| 方案 | 做法 | 为什么没选 / 选 |
|---|---|---|
| A. FFI 嵌入 | Go 内核 cgo 调 Rust staticlib | 跨语言内存与线程边界复杂；Rust 侧 panic 会带崩整个内核进程；构建链（cgo + musl + 交叉编译）脆弱；排障困难 |
| B. 换 Rust 内核 | 用 clash-rs / leaf 这类 Rust 内核 | TUN、DNS、规则引擎、订阅生态都不成熟，等于把「非协议部分」自建一遍，正是策略文档明确说 ROI 最低的部分 |
| **C. Sidecar** | 内核只做 TUN/分流/DNS，出口指向本机 Rust 进程 | **选定** |

### 3.3 选 sidecar 的四条理由

1. **协议零改动**：sidecar 就是节点端同一份代码，两端跑同一实现，协议不可能分叉。
2. **故障隔离**：sidecar 崩了，内核与 UI 不受影响，可单独重启；反过来内核崩了也不影响 sidecar 的日志与诊断。
3. **许可边界清晰**：见第 4 节，这是决定性的一条。
4. **可独立升级**：协议层发版不必连带内核与 UI，灰度成本最低。

### 3.4 代价（必须承认）

- 多一个进程，内存多几 MB（对 1 vCPU 的节点不敏感，对客户端可接受）。
- 需要本地 IPC 鉴权：只监听 `127.0.0.1`、随机端口、每次启动生成 token，否则本机其它程序可白嫖代理。
- 链路变成「TUN → 内核 → SOCKS → sidecar」，多一跳，排障时要多看一层。

### 3.5 链路形态

```
UI（Tauri / 原生）
  │ 本地 IPC
内核（Mihomo fork：TUN / DNS / 规则 / 订阅）
  │ SOCKS5 127.0.0.1:<随机端口> + token
sidecar（Rust：复用 v2node-proto）
  │ VLESS + Encryption + TLS
节点（v2node-rust）
```

## 4. 第三个判断：许可，这条比技术更硬

Mihomo 与 sing-box 都是 **GPL-3.0**。

- 如果是 **FFI 链接**（同一进程内调用），通常会被认定为衍生作品 → 客户端整体需按 GPL 开源。
- 如果是**独立进程 + 标准协议通信**（sidecar 走 SOCKS5），边界更清晰，自研 UI 有闭源空间。

所以「UI 是否必须闭源」这个产品问题，直接决定了技术架构：

- 必须闭源 → **只有 sidecar 可行**；
- 可以开源 → FFI 的工程复杂度才值得讨论。

**这不是法律意见**，正式发布前需要一次许可评审。但架构选择必须现在就按最保守假设做，否则后期改不动。

---

## 5. 第四个判断：平台顺序

选 **Windows 先**，理由三条：

1. 用户基数最大，且分发不经应用商店审核，灰度与回滚都快。
2. TUN/Wintun 与签名方案成熟，调试成本最低。
3. 协议层是同一个 sidecar，Windows 打通后 Android 只需换外壳与 VPN 服务集成。

不做全平台的理由很直接：策略文档已经点名「多平台人力有限时先做一个平台」，而团队目前是「一人 + AI」的实际产能。

---

## 6. 第五个判断：C0 具体做什么

| 事项 | 为什么现在做 | 即使不做客户端是否白做 |
|---|---|---|
| 抽 `v2node-proto` crate | 客户端复用的前提；也让节点代码分层更清晰 | **不白做**，节点本身受益 |
| 加密节点灰度 | 拿覆盖率与握手开销数据，是立项门控 | **不白做**，是节点侧既定路线 |
| Windows 链路 PoC（约 1 人周） | 验证 sidecar 假设是否成立 | 成本可控，可随时停 |

这三件事的共同点：**都不依赖「客户端立项」这个决定**。这是刻意的——避免用「要不要做客户端」卡住本该做的事。

---

## 7. 什么证据会推翻这套方案

写下来是为了让新会话能挑战它，而不是照抄：

1. **抽 crate 成本失控**：如果协议层与 `node.rs`/`panel.rs` 耦合过深（例如 `NodeInfo` 类型到处渗透），拆分可能从 1–2 天变成 1–2 周，届时应先做类型解耦而不是硬拆。
2. **CF 成为硬瓶颈**：如果实测发现瓶颈在 CF/隧道而非协议，那么传输层创新（QUIC / Hysteria2 / 直连入口 / REALITY）的优先级应高于客户端 UI。
3. **内核 TUN 不满足要求**：若 Mihomo 在 Windows 上的 TUN 稳定性或 DNS 行为不达标，可能要换 sing-box 甚至自研外壳。
4. **加密覆盖率数据乐观**：如果目标用户里支持 `encryption` 的客户端版本已占绝大多数，那么「必须自有客户端」的前提就被削弱，可以只做订阅与配置优化。
5. **许可评审结论不同**：若 sidecar 也被认定构成衍生作品，闭源路线不成立，整个产品的分发策略要重排。

## 8. 未决问题（新会话应从这些开始）

1. **内核选型**：Mihomo 还是 sing-box？倾向 Mihomo（规则生态最全、文档多），但 sing-box 的 TUN 实现更现代。
2. **UI 技术栈**：Tauri（复用 Web 技能、体积小）还是原生（WinUI/WPF，系统集成更好）。
3. **订阅格式**：只兼容 Clash YAML，还是同时推自有 `v2node://`（携带 encryption 参数）。后者需要面板配合。
4. **自动更新与签名**：Windows 代码签名证书（EV/OV）、更新 manifest 的签名方案。
5. **团队与预算**：是否只有「一人 + AI」，这决定 C1 是 2 周还是 2 个月。
6. **许可底线**：UI 是否必须闭源——这一条会反向决定架构，必须最先回答。
